# Upgrading from BaGetter

ElPaqueto is a fork of [BaGetter](https://github.com/bagetter/BaGetter), itself a fork of BaGet. The package database schema, its migrations, the storage layout and the configuration keys of the package server (`Database`, `Storage`, `Search`, `Mirror`, ...) are unchanged, so an existing installation keeps its packages. What changed is authentication, and a few names that an installation may rely on without having set them.

Stop BaGetter and back up its database and package storage before you start.

## Breaking change: authentication

ElPaqueto authenticates every request against users and API keys stored, hashed, in its own security database (see [security configuration](configuration.md)). BaGetter's authentication settings are not read any more, and **ElPaqueto refuses to start while one of them is set**:

| BaGetter setting | Replacement |
| --- | --- |
| `ApiKey` | Per-user API keys with the `Publish` permission, created with [`admin key create`](administration.md#api-keys) ([using an API key](configuration.md#using-an-api-key)). |
| `Authentication:ApiKeys` | Same as `ApiKey`: one key per machine or pipeline, each created with `admin key create` and revocable with `admin key revoke`. |
| `Authentication:Credentials` | Users created with [`admin user create`](administration.md#managing-users), with hashed passwords and permissions. |

The startup error names each offending setting and never prints its value:

```text
The setting 'Authentication:Credentials:0:Password' comes from BaGetter and is no longer supported: remove it. ...
```

Remove the settings from every source: `appsettings.json`, environment variables (`ApiKey`, `Authentication__Credentials__0__Username`, ...) and files in `/run/secrets` (for example `/run/secrets/ApiKey`). An empty `ApiKey` (`"ApiKey": ""`, as BaGetter shipped it) is accepted and ignored. Setting names are case-insensitive, so an unrelated environment variable named `APIKEY` (for example set by a CI system or a sidecar) is rejected as well: remove it from the server's environment.

Other consequences:

- **An empty `ApiKey` no longer means an open feed.** Every route except the liveness endpoint and static files requires credentials, and publishing requires an API key with `Publish` sent in the `X-NuGet-ApiKey` header (`dotnet nuget push --api-key`).
- **Clients change.** API keys are `epq_...` tokens generated by ElPaqueto: the values you used with BaGetter do not work. Update `NuGet.Config`, CI secrets and `dotnet nuget push` commands. Reading the feed needs a user password or an API key with `Read` as the source password.
- Plain-text credentials are **not** imported: create the users explicitly. Start with [`admin bootstrap`](administration.md#first-administrator), then create users and their keys, for example:

  ```bash
  dotnet ElPaqueto.dll admin user create ci --permissions publisher --password-file ./ci_password
  (umask 077 && dotnet ElPaqueto.dll admin key create --user ci --name ci-push --permissions publish --expires 90d > ci-push.key)
  ```

  The key is printed once; store it in the CI secret that used to hold the BaGetter `ApiKey`.
- `Mirror:Authentication`, the credentials ElPaqueto sends to the upstream feed when mirroring, is unchanged.

## Default SQLite file: `bagetter.db` is now `elpaqueto.db`

When the connection string is not set, the default SQLite file is `elpaqueto.db` (in the Docker image, `/data/db/elpaqueto.db`). An installation that relied on the default `bagetter.db` would otherwise start on a new, empty database: the packages are still in storage, but the feed lists nothing.

At startup, when the configured SQLite file does not exist and a `bagetter.db` file is in the same folder, ElPaqueto logs a warning naming both files, then starts and creates the new, empty database. It never renames or opens the old file. The warning is logged only while the configured file does not exist, so act on the first one. Either:

- set the connection string to the existing file, for example `Database__ConnectionString="Data Source=/data/db/bagetter.db"`, or
- stop ElPaqueto, delete the new `elpaqueto.db` if one was created (and its `-wal` and `-shm` files), rename `bagetter.db` to `elpaqueto.db` (with its `-wal` and `-shm` files, if any), and start again.

Other database types (PostgreSQL, SQL Server, Azure Table) are not affected.

## `BAGET_CONFIG_ROOT` is now `ELPAQUETO_CONFIG_ROOT`

The environment variable that names the folder of `appsettings.json` is `ELPAQUETO_CONFIG_ROOT`. `BAGET_CONFIG_ROOT` is still read when `ELPAQUETO_CONFIG_ROOT` is not set, with a deprecation warning at startup; when both are set, `ELPAQUETO_CONFIG_ROOT` wins. Rename the variable: the fallback will be removed in a later release.

## Logging categories: `BaGetter.*` is now `ElPaqueto.*`

Log categories follow the namespaces, which are now `ElPaqueto.*`. A filter such as `Logging:LogLevel:BaGetter.Core` no longer applies: rename it, for example to `Logging:LogLevel:ElPaqueto.Core`.

## Outbound `User-Agent`

When mirroring, requests to the upstream feed carry the `User-Agent` `ElPaqueto/<version>` instead of `BaGetter/<version>`. Update any upstream allow-list or log filter that matches on it.

## Configuration files that cannot be read

A configuration file that the server cannot read or parse, such as `appsettings.json` or a file in `/run/secrets` that the container user (UID 1654) cannot read, stops the server and every command with exit code 1 and the message `ElPaqueto could not load its configuration: ...`, naming the file. See [Docker](docker.md#running-the-container) for the ownership of secret files.
